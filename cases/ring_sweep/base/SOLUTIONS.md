# Ring Sweep Case — Diagnosis & Fix Strategy

## Symptoms

1.  **Forces on `ringSurface` are all zero** — physically impossible for a ring
    moving at 2 m/s through water.
2.  **Velocity field looks static** — the ring doesn't appear to interact with
    the fluid.
3.  **`alpha.water` in air region shows denormal values** — probes 7–9
    (z = 0.4–0.5) report values in the 1e-80 to 1e-270 range.

## Root Cause

The ring is a thin flat annulus generated by `generate_ring.py`:

| Parameter        | Symbol | Value       |
|------------------|--------|-------------|
| Outer diameter   | D      | 0.05 m      |
| Radial wall      | t      | 0.0025 m    |
| Height           | w      | 0.01 m      |
| Centre z         | cz     | 0.35 m      |

At snappyHexMesh refinement **level 4**, the cell size in x,y is
0.3 m / 20 / 2⁴ ≈ 0.94 mm.  The radial wall is only 2.5 mm thick, so there are
≈2.7 cells across the wall.  **No cell centre falls strictly inside the
annular volume.**  Consequently:

1.  `cellZoneInside inside` → **ringZone is empty** (0 cells)
2.  `ringSurface` / `ringSurface_slave` boundary patches are removed because
    they have zero faces
3.  `solidBody` motion solver has nothing to move → **ring does not move**
4.  `forces` function object cannot find `ringSurface` → **forces are always
    zero**
5.  The existing `topoSetDict` does `zoneToCell` on the (empty) `ringZone` →
    also produces 0 cells

The simulation was effectively a **static-mesh VOF** run with no ring motion.

## Fix Strategy

### 1. Cell zone: `cylinderToCell` in topoSet (geometric creation)

**Problem**: `snappyHexMesh` `cellZoneInside inside` requires cell *centres* to
fall inside the STL volume. With a 2.5 mm wall and ~0.94 mm cells this fails.

**Fix**: `topoSet`'s `cylinderToCell` source selects cells by **bounding-box
intersection**, not centre-point containment. We create two cylinders and
subtract:

```
ringOuter = cylinderToCell(R=0.025, z=[0.345, 0.355])
ringInner = cylinderToCell(R=0.0225, z=[0.345, 0.355])
ringZone  = ringOuter - ringInner
```

This robustly populates the cell zone regardless of wall thinness.

### 2. Forces: boundary patch from snappyHexMesh

**Problem**: When snappyHexMesh has `cellZone` + `cellZoneInside`, the STL
surface faces become *internal* `faceZone` faces (between the cell zone and
the exterior). Boundary patches are not created.

**Fix**: Remove `cellZone` and `cellZoneInside` from
[`system/snappyHexMeshDict`](system/snappyHexMeshDict).  With only `faceZone`
and `patchInfo` specified, snappyHexMesh creates `ringSurface` as a **wall
boundary patch**. The forces function object can then compute forces on it.

The STL's deliberate puncture (2 segments / 60 = 3 % of the top cap) creates
a small hole in the boundary patch. This introduces a ~3 % force error (the
hole area), but is necessary because a watertight STL would cause
snappyHexMesh to remove interior cells (disconnected region) and we would
lose the potential cell zone.

### 3. Refinement increase

snappyHexMesh refinement at the ring surface increased from `(4 4)` to
`(5 6)` for better surface representation.

### 4. Alpha denormal cleanup

The 1e-80–1e-270 `alpha.water` values in the air region are floating-point
underflow noise from the MULES alpha equation. They are too small to affect
the momentum solution but indicate imperfect boundedness. This is a cosmetic
issue — OpenFOAM's `incompressibleVoF` solver clips alpha to [0,1] in
post-processing for visualisation.

## Verification Checklist

After re-running (`./Allclean && ./Allrun`):

```bash
# 1. ringZone should have > 0 cells
grep -A 5 "cellZone" log.topoSet
# Expected: ringZone new, size > 0

# 2. ringSurface should be in the boundary
grep "ringSurface" log.checkMesh.refined

# 3. No "Cannot find any patch" warnings in solver log
grep "Cannot find" log.foamRun
# Expected: no output

# 4. Forces should be non-zero after ring contacts water
# Check postProcessing/forces/0/forces.dat after run
```
